## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **รับของรางวัลแล้วง่ายขึ้น ไม่ต้องบอกชื่อ/รหัสนักศึกษาเอง** ตอนไปรับของรางวัลไม่ว่าจะเป็นรางวัลในงานหรือของแจกที่ต้องมารับทีหลัง (เช่น แก้ว) เจ้าหน้าที่จะสแกน QR โค้ดของนักศึกษาแทนการจดชื่อ ทำให้เร็วขึ้นและไม่พลาดเรื่องข้อมูลผิด และอาจมีการถ่ายรูปตอนรับของไว้เป็นหลักฐานด้วย

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **เมนูใหม่ "การรับรางวัล" (`/admin/prizes`) สำหรับบันทึกการแจกของรางวัลทุกชนิด** ไม่ว่าจะเป็นรางวัลที่แจกในงานกิจกรรมหรือของแจกที่ให้มารับนอกรอบ (เช่น แก้ว) ก็บันทึกในที่เดียวกันได้ ตั้งค่าได้ว่ารางวัลนี้รับได้คนละครั้งเดียวไหม และต้องเช็คอินกิจกรรมไหนก่อนถึงมีสิทธิ์รับ โดยระบบจะกันไม่ให้คนเดิมรับซ้ำในระดับฐานข้อมูลเลย ต่อให้พยายามรับสองรอบจากเครื่องคนละเครื่องพร้อมกันก็ยังกันได้
- **แจกของผ่านหน้าจอสแกน QR เหมือนเครื่องสแกนเช็คอิน** เลือกรางวัลแล้วสแกน QR นักศึกษา ระบบจะขึ้นชื่อ-รหัสให้ทันที กดยืนยันแล้วค่อยถ่ายรูปนักศึกษาถือของทีหลังได้ ไม่ต้องรอรูปเสร็จก่อนถึงจะบันทึกได้ กันเน็ตล่มแล้วพลาดบันทึกที่บูธ ถ้าใครสแกนไม่ได้ก็ค้นหาด้วยชื่อ/รหัสแทนได้ **SMO ก็แจกรางวัลผ่านหน้านี้ได้เหมือนเดิมที่แจกในเครื่องสแกน** แต่การออกรายงานและตั้งค่ารางวัลใหม่ยังต้องเป็นแอดมิน/องค์กร/ประธานชมรม-สาขาเท่านั้น
- **ออกรายงานส่งคณบดีได้ 2 แบบ** ไฟล์ Excel ที่แก้ไขได้พร้อมรูปถ่ายฝังอยู่ในไฟล์ กับหน้าเว็บสำหรับสั่งพิมพ์เป็น PDF ที่รูปจะติดอยู่กับชื่อคนแน่นอนไม่มีทางสลับ (ต่างจากไฟล์ Excel ที่ถ้ามีคนลอง sort/filter ตาราง รูปที่ฝังไว้จะไม่เลื่อนตามแถวไปด้วย จึงต้องใช้ PDF เป็นตัวหลักฐานจริง)

## ฝั่งทีม (technical changelog)

### เพิ่มระบบการรับรางวัล (การรับรางวัล) พร้อมกันข้อมูลซ้ำระดับฐานข้อมูล (PR #237, merge commit `58681f3`)

- **Feature:** เพิ่มตาราง `prizes` และ `prize_claims` โดย **รางวัลไม่ได้ผูกเป็นลูกของอีเวนต์** แต่ผูกกับอีเวนต์แบบ optional เท่านั้น (`event_id` เป็น `SET NULL`) เพราะของแจกอย่างแก้วอาจแจกทั้งในงานและที่เคาน์เตอร์วันหลัง ถ้าผูกความไม่ซ้ำไว้กับอีเวนต์จะทำให้เปิดรอบรับรอบสองแล้วรับซ้ำได้ การกันซ้ำจึงผูกไว้กับตัวรางวัลเองผ่าน **partial unique index** `(prize_id, student_id) WHERE one_per_student` ที่ระดับ Postgres ซึ่งกันได้แม้สแกนพร้อมกันสองเครื่องในวินาทีเดียวกัน (ทดสอบ race นี้จริงแล้วผ่าน)
- **เงื่อนไขเช็คอินก่อนรับ:** ตั้งค่าได้ต่อรางวัลว่าต้องเช็คอินกิจกรรมไหนก่อนถึงมีสิทธิ์รับ (`requireCheckIn` + `eligibilityEventId` แยกจาก `event_id` ที่ใช้บอกแค่บริบทของรางวัล) และปรับ query รายงานให้ pre-aggregate จำนวนวันที่เช็คอินก่อน join เพราะกิจกรรมหลายวันมี attendance หลายแถวต่อคน ถ้า join ตรง ๆ ผู้ชนะคนเดียวจะโผล่ซ้ำในรายงานหลายบรรทัด
- **PDPA:** รูปหลักฐานการรับของเก็บใน private bucket เดียวกับรูปหลักฐาน evidence check-in (ไม่ใช่ public URL) เสิร์ฟผ่าน route ที่ auth แล้วเท่านั้น และทุกครั้งที่มีคนอื่น (ไม่ใช่เจ้าของรูป) เปิดดูหรือดาวน์โหลดรายงานจะถูกบันทึกลง audit log เก็บรูปไว้ไม่มีกำหนดจนกว่า super_admin จะลบ ลบได้เฉพาะรูป แถวบันทึกการรับยังอยู่เสมอ ไม่งั้นระบบกันซ้ำจะลืมว่าคนนี้เคยรับไปแล้ว
- **สิทธิ์เข้าถึง:** แยกสิทธิ์ "แจกรางวัล" (`canAwardPrizes` รวม smo ด้วยเพราะแจกทีละคนต่อหน้า) ออกจาก "ตั้งค่ารางวัล/ออกรายงาน" (`canManagePrizes`/`canExportPrizeReport` ไม่รวม smo เพราะรายงานคือรายชื่อ+รหัส+รูปหน้าทั้งงานในไฟล์เดียว) ประธานชมรม/สาขาถูก scope ให้เห็นเฉพาะรางวัลที่ผูกกับอีเวนต์ของชมรม/สาขาตัวเองผ่าน `EventScopeService` เดียวกับที่ใช้ในหน้า attendance/appeals ทดสอบแล้วว่าประธานคนละชมรมมองไม่เห็นรางวัลของกันและกัน
- **รายงาน:** ไฟล์ `.xlsx` ใช้ `exceljs` (ไม่ใช่ `xlsx` ที่ export อื่นใช้) เพราะ SheetJS community build ที่ pin ไว้ฝังรูปในไฟล์ไม่ได้ ย่อรูปด้วย `sharp` เหลือด้านยาว 320px ก่อนฝัง กันไฟล์ใหญ่เกินไป และเขียนวันที่เป็น real Excel date cell (ไม่ใช่ string) เพื่อให้ sort ได้ถูกต้อง หน้ารายงาน PDF ใช้ query เดียวกันกับ Excel เป๊ะ ๆ ผ่านการสั่งพิมพ์จากเบราว์เซอร์ ไม่ต้องเพิ่ม PDF library
- **Migration:** เพิ่ม step 94 ใน `src/db/migrate.ts` (ตัวสคริปต์ที่ `db:migrate`/`db:migrate:container` รันจริงกับ Postgres) เพราะ `db:generate` สร้างไฟล์ `drizzle/0042` ให้เฉยๆ ไม่ได้ทำให้ตารางไปสร้างบน Postgres จริงโดยอัตโนมัติ ถ้าไม่เพิ่ม step นี้ทุก route ของฟีเจอร์นี้จะ error บน prod ทันทีหลัง deploy ทั้งที่ build ผ่าน (เจอระหว่างรัน `/verify` กับ local DB ก่อน merge)
- **แก้บั๊กที่เจอตอนทดสอบจริง:** route ที่รับ id ของรางวัลจาก URL (`claim`, แก้ไขรางวัล, export, หน้ารายงาน) ไม่ได้ตรวจรูปแบบ id ก่อน query ทำให้ id ที่หายไปหรือผิดรูปแบบหลุดไปถึง Postgres ตรง ๆ จน error ดิบโผล่ใน log แทนที่จะตอบ 400 สั้น ๆ แก้แล้วทุก route ให้ตรวจก่อนเหมือน route รูปหลักฐานที่มีการตรวจอยู่แล้ว
- ตรวจสอบแล้วด้วย `npm run lint`, `npx tsc --noEmit`, `npm run build`, `npm test` (289 tests) ผ่านครบ พร้อมทดสอบจริงกับ local DB ผ่าน dev-bypass session (ยิง API ตรง ไม่ mock): กันรับซ้ำทั้งจาก SQL ตรงและผ่าน API, เงื่อนไขเช็คอินก่อนรับ, การจัดกลุ่มไม่ให้รายงานซ้ำในกิจกรรมหลายวัน, เนื้อหาไฟล์ Excel จริง (วันที่/รูปที่ฝัง), ลบรูปแล้วแถวยังกันซ้ำได้ต่อ, ลบรางวัลแล้ว claims/รูปถูกลบตามจริง

### แก้ log การส่ง push notification ที่ล้มเหลวไม่มีร่องรอย (PR #236, merge commit `8a9fe56`)

- **Bug:** ตอนก่อนหน้านี้ ถ้าส่ง push แล้วล้มเหลว (เช่น VAPID key ผิด, VAPID_SUBJECT ผิดรูปแบบ, หรือ push service ปฏิเสธ) โค้ดจะแค่อัปเดต `failureCount`/ลบ subscription ทิ้งเงียบ ๆ โดยไม่ log อะไรเลย ทำให้เวลาการส่งจริงมีปัญหาบน prod ไม่มีทางรู้สาเหตุได้เลยถ้าไม่เข้าไปดู DB ตรง ๆ
- **แก้ไข:** log รหัส subscription, status code, และข้อความ error จาก push service เอง (ไม่ log endpoint URL เต็มเพราะเป็นข้อมูลระบุตัวอุปกรณ์)

# ActiveCAMT v2.10.1 🎉

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **แก้หน้าจอ "การรับรางวัล" ที่อ่านไม่ออกบนมือถือที่ตั้งเป็นโหมดมืด** ถ้ามือถือของเจ้าหน้าที่ตั้งธีมเป็นมืดไว้ หน้าต่างสร้างรางวัลและหน้าสแกนแจกรางวัลที่เพิ่งเปิดใช้เมื่อกี้จะขึ้นพื้นหลังสีเข้มแต่ตัวหนังสือยังเป็นสีเดิม ทำให้อ่านไม่ออกหรือดูเหมือนตัวหนังสือซ้อนกัน ตอนนี้แก้ให้ใช้สีเดียวกับหน้าแอดมินอื่น ๆ ทั้งระบบ อ่านออกชัดเจนไม่ว่ามือถือจะตั้งธีมแบบไหน และปรับให้ช่องตั้งค่าต่าง ๆ กดง่ายขึ้นด้วย เพราะหน้านี้ใช้งานบนมือถือหน้าบูธเป็นหลัก

## ฝั่งทีม (technical changelog)

- **Bug:** `PrizesClient.tsx` และ `PrizeAwardPanel.tsx` เป็นไฟล์เดียวในทั้ง `src/app/admin` ที่ใช้ Tailwind `dark:` classes ทั้งที่แอปนี้ตั้งใจให้เป็น light-only เท่านั้น (`color-scheme: only light` ใน `globals.css`) เพราะถ้าปล่อยให้ dark mode ทำงาน QR โค้ดเช็คอินสีดำบนขาวจะถูกกลับสีจนเครื่องสแกนอ่านไม่ออก พอมือถือเจ้าหน้าที่ตั้งโหมดมืดไว้ `dark:` classes เหล่านี้เลยทำงานแต่ตัวหนังสือไม่มีสีสำหรับโหมดมืดคู่กัน ทำให้อ่านไม่ออก
- **แก้ไข:** เขียนใหม่ทั้งสองไฟล์ให้เลิกใช้ `dark:` classes ทั้งหมด เปลี่ยนไปใช้ระบบ component เดิมของแอป (`.btn`/`.input`/`.field`/`.label`/`.badge` และ CSS variable tokens จาก `globals.css`) กับ modal แบบ portal เหมือนหน้า `admin/clubs/page.tsx` และหน้าผลสแกนของเครื่องสแกน กันไม่ให้ modal ถูกซ้อนผิดตำแหน่งจาก ancestor ที่มี transform ด้วย
- **Human factors:** ปรับ checkbox ตั้งค่า ("1 คนรับได้ครั้งเดียว", "ต้องเช็คอินก่อน") ให้เป็นแถวที่กดได้ทั้งแถวแทนกล่องเล็ก ๆ และปุ่มในหน้าสแกนแจกรางวัลใหญ่ขึ้น เพราะหน้านี้ถูกใช้บนมือถือที่ถืออยู่ในระยะเอื้อมมือหน้าบูธ
- ตรวจสอบแล้วด้วย `npm run lint`, `npx tsc --noEmit`, `npm run build` ผ่านครบ พร้อมทดสอบจริงผ่าน dev-bypass session กับ local DB โดยเปิดหน้าสร้างรางวัล ตรวจ toggle ทั้งสองแถว และเดินผ่าน flow สแกน เห็นตัวอย่าง ยืนยัน ถ่ายรูป จนจบ ไม่พบร่องรอยของโหมดมืดหลงเหลือ

# ActiveCAMT v2.10.2 🎉

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **แก้กล้องสแกนแจกรางวัลที่กรอบดูเหมือนไม่อยู่ตรงกลาง** กล้องบนหน้าสแกนแจกรางวัลก่อนหน้านี้ไม่ได้ขอภาพจากกล้องเป็นสัดส่วนสี่เหลี่ยมจัตุรัส ทำให้กล้องบางเครื่อง (เช่นเว็บแคมโน้ตบุ๊ก) ได้ภาพทรงสูงเกินไปจนกรอบสแกนดูเหมือนไม่อยู่ตรงกลาง ตอนนี้ขอภาพเป็นสี่เหลี่ยมจัตุรัสแล้ว กรอบสแกนจึงอยู่ตรงตำแหน่งที่ควรอยู่
- **หน้าการรับรางวัลตอนนี้ดูเหมือนหน้าแอดมินอื่น ๆ แล้ว** ก่อนหน้านี้หน้านี้มีระยะห่างและหัวข้อของตัวเองแยกจากหน้าอื่น ทำให้ดูไม่กลมกลืนกับหน้าอื่นในระบบแอดมิน ตอนนี้ปรับให้ใช้สไตล์เดียวกับหน้าคำอุทธรณ์และหน้ารอตรวจสอบแล้ว
- **หน้าการรับรางวัลรองรับการเปลี่ยนภาษาแล้ว** ก่อนหน้านี้หน้านี้เป็นภาษาไทยล้วนไม่ว่าจะสลับภาษาระบบเป็นอะไรก็ตาม เป็นจุดเดียวในหน้าแอดมินที่ไม่รองรับการสลับภาษา ตอนนี้รองรับครบทั้ง 4 ภาษาแล้วเหมือนหน้าอื่น ๆ

## ฝั่งทีม (technical changelog)

- **Bug (กล้อง):** `PrizeAwardPanel.tsx` ไม่เคยส่ง `aspectRatio` ให้ `html5-qrcode` ตอนเปิดกล้อง ทำให้กล้องได้ความละเอียดตามธรรมชาติของอุปกรณ์ (ซึ่งมักเป็นแนวตั้งสูง) กรอบสแกนที่จริง ๆ อยู่กึ่งกลางของภาพอยู่แล้วจึงดูเหมือนไม่อยู่ตรงกลางเมื่อเทียบกับกรอบกล้องทั้งหมด แก้โดยขอ `aspectRatio: 1` จากกล้องและปรับกล่องกล้องให้เป็นสี่เหลี่ยมจัตุรัสตามไปด้วย
- **Layout:** `PrizesClient.tsx` มี wrapper ของตัวเองที่กำหนด max-width และ padding ซ้ำซ้อนกับ `AdminLayoutWrapper` ที่จัดการ padding ให้อยู่แล้ว ทำให้หน้าดูแคบและตำแหน่งหัวข้อไม่ตรงกับหน้าอื่น แก้โดยตัด wrapper ที่ซ้ำซ้อนออกและใช้โครงหัวข้อแบบเดียวกับ `admin/appeals` และ `admin/reviews`

# ActiveCAMT v2.10.3 🎉

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **กรอบสแกน QR ในหน้าแจกรางวัลอยู่ตรงกลางจริง ๆ แล้ว** รอบที่แล้วขอให้กล้องส่งภาพเป็นสี่เหลี่ยมจัตุรัสแล้ว แต่กล้องบางรุ่น (เช่นเว็บแคมโน้ตบุ๊กบางรุ่น) ไม่ยอมทำตามที่ขอจริง ๆ ยังส่งภาพเป็นสัดส่วนอื่นอยู่ ทำให้กรอบสแกนดูเหมือนค้างอยู่ด้านบนของกล่องกล้อง ตอนนี้แก้ให้ภาพจากกล้องอยู่ตรงกลางกล่องเสมอไม่ว่ากล้องจะส่งภาพสัดส่วนไหนมาก็ตาม
- **หน้าต่างแจกรางวัลอยู่กึ่งกลางจอแล้ว** ก่อนหน้านี้หน้าต่างนี้เด้งขึ้นมาจากด้านล่างจอแบบ bottom sheet ซึ่งไม่เหมือนกับหน้าต่างอื่น ๆ ในระบบแอดมิน (เช่นหน้าต่างสร้าง/แก้ไขชมรม) ตอนนี้ปรับให้อยู่กึ่งกลางจอเหมือนหน้าต่างอื่นแล้ว

## ฝั่งทีม (technical changelog)

- **Bug (กล้อง):** `aspectRatio: 1` ที่ส่งให้ `html5-qrcode` เป็นแค่คำขอ ไม่ใช่การบังคับ กล้องหลายรุ่นเพิกเฉยแล้วส่งภาพตามสัดส่วนธรรมชาติของตัวเองแทน (เช่น 4:3) ขณะที่ `html5-qrcode` กำหนดความกว้างของ `<video>` ตามกล่องคอนเทนเนอร์แต่ปล่อยความสูงเป็น auto โดยไม่จัดกึ่งกลางให้ พอภาพที่ได้ไม่เป็นสี่เหลี่ยมจัตุรัสจริง วิดีโอ (และกรอบสแกนที่ซ้อนอยู่บนวิดีโอ) จึงเตี้ยกว่ากล่องสี่เหลี่ยมและติดอยู่ด้านบนตามพฤติกรรม default ของ block element แก้โดยปรับ wrapper `#prize-qr-reader` ให้เป็น flex container แบบจัดกึ่งกลาง ทำให้วิดีโอกึ่งกลางกล่องเสมอไม่ว่าสัดส่วนจริงจากกล้องจะเป็นเท่าไหร่
- **UI:** overlay ของหน้าต่างแจกรางวัลใช้ `alignItems: "flex-end"` ทำให้เป็น bottom sheet มุมบนตัดตรง ต่างจากหน้าต่างอื่นในระบบแอดมินที่ใช้ `alignItems: "center"` ทั้งหมด (เช่นหน้าต่างของ `admin/clubs/page.tsx` และ overlay ในหน้าเครื่องสแกน) แก้ให้ตรงกับรูปแบบเดิมของระบบ
- ตรวจสอบแล้วด้วย `npm run lint`, `npm run build` ผ่านครบ (error เดียวที่เจอเป็นของเดิมในไฟล์ทดสอบที่ไม่เกี่ยวข้อง `battle-flow.test.ts`) และตรวจ DOM จริงผ่าน dev-bypass session โดยจำลององค์ประกอบขนาดเท่าที่ `html5-qrcode` สร้างจริง (กว้างคงที่ สูง auto ไม่เท่าคอนเทนเนอร์) เพื่อยืนยันว่าจัดกึ่งกลางได้จริงโดยไม่ต้องพึ่งกล้องจริง เพราะสภาพแวดล้อมทดสอบไม่มีกล้องให้เชื่อมต่อ
