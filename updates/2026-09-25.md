สรุปสำหรับวันที่ 25 ก.ย. 69 เอาไว้ลง Discord และให้ทีมที่เกี่ยวข้องอ่านกัน

## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **ร้านค้ามีโปรโมชันซื้อหลายชิ้นราคาพิเศษแล้ว** เช่น "ซื้อ 3 ชิ้น ฿100" สินค้าที่มีโปรจะมีป้ายสีเขียวบอกไว้ที่การ์ดสินค้าและในหน้าสั่งซื้อ พอสั่งครบจำนวน ระบบจะหักส่วนลดให้อัตโนมัติ และโชว์บรรทัด "ส่วนลดโปรโมชัน" ในสรุปยอดก่อนโอนเงิน จะได้โอนตามยอดที่ถูกต้องเลย
- **ระบบเลือกราคาที่ถูกที่สุดให้เสมอ** ถ้าสินค้ามีหลายโปร เช่น 3 ชิ้น ฿100 และ 5 ชิ้น ฿150 ระบบจะคำนวณการจับคู่ที่คุ้มที่สุดให้เอง ส่วนชิ้นที่เหลือเกินโปรจะคิดราคาปกติ
- **ในหน้า "คำสั่งซื้อของฉัน" จะเห็นด้วยว่าประหยัดไปเท่าไร** ในแต่ละออร์เดอร์ที่ได้ส่วนลด

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **ตั้งโปรโมชันให้สินค้าได้เองในหน้าเพิ่ม/แก้ไขสินค้า** มีหัวข้อใหม่ "โปรโมชัน (ซื้อหลายชิ้นราคาพิเศษ)" ให้กรอกว่าซื้อกี่ชิ้นในราคาเท่าไร ตั้งได้สูงสุด 5 โปรต่อสินค้า และระบบจะบอกทันทีว่าลูกค้าประหยัดไปกี่บาทต่อโปร
- **โปรนับรวมทุกไซส์/ตัวเลือกของสินค้าเดียวกันในออร์เดอร์เดียว** ส่วนไซส์พิเศษที่บวกเงินเพิ่ม (เช่น XXL +฿20) ยังคิดเพิ่มตามปกติ
- **เห็นส่วนลดชัดเจนตอนตรวจสลิป** การ์ดออร์เดอร์ในหน้าจัดการร้านค้ามีบรรทัด "ส่วนลดโปรโมชัน" แยกออกมาก่อนยอดรวม เทียบกับยอดในสลิปได้ง่าย และไฟล์ Excel ที่ส่งออกมีคอลัมน์ "Promotion discount (THB)" เพิ่มเข้ามาด้วย รายการสินค้าในหน้าแอดมินก็โชว์โปรต่อท้ายราคาให้เห็นเลย
- **แก้จำนวนในออร์เดอร์แล้วส่วนลดคำนวณใหม่ให้เอง** ถ้าแอดมินแก้จำนวนชิ้นจนถึงหรือต่ำกว่าเงื่อนไขโปร ระบบจะคิดส่วนลดใหม่ตามจำนวนใหม่ แต่ถ้าแก้แค่โน้ตหรือที่อยู่ ส่วนลดเดิมจะไม่ถูกแตะ
- ผู้ขาย/ประธานชมรมที่ตั้งหรือแก้โปรจะต้องรอผู้ตรวจอนุมัติสินค้าใหม่เหมือนการแก้ไขสินค้าแบบอื่น

## ฝั่งทีม (technical changelog)

### โปรโมชันแบบ bundle "ซื้อ N ชิ้น ฿X" สำหรับสินค้าในร้านค้า (PR #259, merge commit `c582382`)

- **Pricing logic:** เพิ่ม `src/lib/shop-promotions.ts` เป็น source of truth เดียว (`computeBundleCost`, `computeBundleDiscount`, `normalizeBundleDeals`, `bundleDealSchema`) ใช้ร่วมกันทั้ง storefront, `POST /api/shop/orders` และ `PUT /api/admin/shop/orders/[id]` คำนวณราคาที่ถูกที่สุดด้วย DP แบบ unbounded knapsack แทน greedy เพราะการเลือกโปรชิ้นใหญ่สุดก่อนไม่ได้ถูกที่สุดเสมอ พร้อม unit test 8 เคสใน `shop-promotions.test.ts`
- **Checkout:** ส่วนลดคำนวณฝั่ง server เท่านั้น นับจำนวนต่อสินค้ารวมทุก variant ในออร์เดอร์เดียว คิดจากราคาฐานเท่านั้น (priceDelta ของ variant ยังบวกเพิ่มตามเดิม) แล้ว snapshot ไว้ที่ `shop_orders.discount_amount` โดยแต่ละบรรทัดยังเก็บ `unitPrice` เต็มเหมือนเดิม สูตรยอดรวมคือ ผลรวมบรรทัด ลบส่วนลด บวกค่าส่ง
- **Admin order edit:** คำนวณส่วนลดใหม่เฉพาะตอนที่จำนวนเปลี่ยนจริงเท่านั้น ใช้กติกาเดียวกับค่าส่งแบบขั้นบันได เพื่อไม่ให้การแก้ไขที่ไม่เกี่ยวกับจำนวนไปขยับยอดที่ snapshot ไว้แล้ว
- **Validation:** `productSchema` รับ `bundleDeals` ได้สูงสุด 5 รายการ จำนวนต้องไม่น้อยกว่า 2 และ route เรียก `normalizeBundleDeals` ก่อนบันทึก (ตัดแถวไม่ครบ รวมจำนวนที่ซ้ำโดยยึดค่าล่าสุด และเรียงจากน้อยไปมาก) การแก้โปรโดยผู้ขายที่ถูก scope ไว้ยังเข้าคิวตรวจใหม่ผ่าน `needsReReview` เหมือนเดิม
- **DB/migration:** เพิ่ม `shop_products.bundle_deals` (jsonb, nullable) และ `shop_orders.discount_amount` (integer, default 0) เป็นแบบ additive และ idempotent ทั้งหมด มีทั้ง `drizzle/0044_sour_king_bedlam.sql` และ **`migrate.ts` step 96** ซึ่งเป็นเส้นทางที่ prod รันจริง เพราะระหว่าง `/verify` พบว่า `migrate.ts` ไม่ได้อ่านไฟล์ drizzle บน Postgres ถ้าลืมเพิ่ม step นี้ prod จะไม่ได้คอลัมน์ใหม่เลย migrate prod ผ่าน Portainer เรียบร้อยก่อน merge
- **ตรวจสอบแล้ว:** `npm test` ผ่าน 304 เคส, `tsc`, `npm run build` ผ่าน ส่วน lint ไม่มี error ใหม่ (error เดียวเป็นของเดิมใน `battle-flow.test.ts`) และ `/verify` กับฐานข้อมูล local สั่งซื้อจริงผ่าน API ได้ยอดตรงทุกเคส ได้แก่ 3 ชิ้น ฿100, 2S+1XXL ฿120 (บวก XXL ครบ), 8 ชิ้น ฿250 (5+3) และ 2 ชิ้น ฿80 (ไม่ถึงโปร) แอดมินแก้จำนวนจาก 2 เป็น 3 ราคาปรับจาก ฿80 เป็น ฿100 ถูกต้อง และแก้แค่โน้ตแล้วส่วนลดไม่เปลี่ยน พร้อม screenshot หน้าร้าน สรุปยอด ฟอร์มแอดมิน และการ์ดออร์เดอร์ ไม่มี console error

# ActiveCAMT v2.14.1 🎉

## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **สั่งหลายไซส์ในออร์เดอร์เดียวได้แล้ว** หน้าต่างสั่งซื้อเปลี่ยนจากเลือกไซส์ได้ทีละไซส์ มาเป็นปุ่มเพิ่ม/ลดจำนวนแยกของแต่ละไซส์ เช่น สั่ง S 2 ตัว M 1 ตัว ในคราวเดียว โอนเงินและแนบสลิปครั้งเดียวจบ ไม่ต้องแยกสั่งหลายรอบอีกต่อไป
- **เห็นชัดว่าแต่ละไซส์เหลือกี่ชิ้นและบวกเพิ่มเท่าไร** ไซส์ที่หมดจะเป็นสีจางกดไม่ได้ ถ้าสั่งครบจำนวนที่จำกัดต่อคนแล้ว ปุ่มเพิ่มจะกดไม่ได้เอง และมีบรรทัดบอกว่ารวมทั้งหมดกี่ชิ้น
- **ได้โปรซื้อหลายชิ้นง่ายขึ้น** เพราะโปรอย่าง "ซื้อ 3 ชิ้น ฿100" นับรวมทุกไซส์ในออร์เดอร์เดียวอยู่แล้ว ตอนนี้จึงคละไซส์ให้ครบโปรได้จากหน้าร้านโดยตรง
- สินค้าที่มีตัวเลือกเดียวยังหน้าตาและใช้งานเหมือนเดิมทุกอย่าง

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- ออร์เดอร์ที่คละไซส์จะแสดงเป็นหลายบรรทัดในการ์ดออร์เดอร์และไฟล์ Excel เหมือนออร์เดอร์หลายรายการทั่วไป โดยข้อมูลที่ผู้ซื้อกรอก (เช่น ชื่อบนเสื้อ) จะติดไปกับทุกบรรทัดของสินค้านั้น

## ฝั่งทีม (technical changelog)

### สั่งหลายไซส์ในออร์เดอร์เดียว (PR #260, merge commit `5fcefc4`)

- **Storefront เท่านั้น:** แก้ `src/app/dashboard/shop/ShopClient.tsx` ไฟล์เดียว เปลี่ยน state จาก `variantId` เดียวกับ `qty` เดียว มาเป็น `qtyByVariant` และ `customValueByVariant` แล้วส่ง `items` หลายรายการไปที่ `POST /api/shop/orders` ซึ่งรองรับอยู่แล้ว (ตรวจ stock ต่อ variant, `maxPerOrder` รวมทั้งสินค้า และส่วนลด bundle รวมทุก variant) จึงไม่มีการแก้ API หรือ schema และไม่ต้อง migrate
- ปุ่มเพิ่มจำกัดด้วย stock ที่เหลือของแต่ละ variant (และ 99 ตามที่ API รับต่อรายการ) กับ `maxPerOrder` ที่นับรวมทุกแถว ราคา ส่วนลด และค่าส่งแบบขั้นบันไดคำนวณจากจำนวนรวมของสินค้าเหมือนฝั่ง server
- สินค้าที่มีหลายตัวเลือกเริ่มที่ 0 ทุกไซส์และปุ่ม "ดำเนินการต่อ" ปิดไว้จนกว่าจะเลือก ส่วนสินค้าตัวเลือกเดียวเริ่มที่ 1 เหมือนเดิม ช่อง "ระบุเอง" แยกต่อ variant และขึ้นเมื่อจำนวนมากกว่า 0 เท่านั้น
- **ตรวจสอบแล้ว:** `npm test` ผ่าน 304 เคส, `tsc`, `npm run build` ผ่าน lint ไม่มี warning ใหม่ และ `/verify` ในเบราว์เซอร์กับฐานข้อมูล local ด้วยเสื้อ ฿100 (จำกัด 4 ตัวต่อคน, S เหลือ 2, XL +฿30, มีตัวเลือกระบุเอง, บังคับกรอกชื่อ, โปร 3 ตัว ฿250) ปุ่มเพิ่ม S หยุดที่ 2 ตาม stock ปุ่มเพิ่ม M หยุดเมื่อรวมครบ 4 ตัว และสั่งจริง S 2 ตัว M 1 ตัว "Other: 3XL" 1 ตัว ได้ยอด ฿350 (ลด ฿50) ตรงกับที่หน้าจอแสดง ไม่มี console error
