## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **ระบบให้ตรวจสอบข้อมูลส่วนตัวทุก 3 เดือน** เมื่อเข้าหน้าแรกหรือหน้าโปรไฟล์ จะมีป๊อปอัปถามว่า "ข้อมูลของคุณยังเป็นปัจจุบันอยู่ไหม" เพื่อให้ข้อมูลส่วนตัว ข้อมูลสุขภาพ และผู้ติดต่อฉุกเฉินถูกต้องอยู่เสมอ ทีมงานจะได้ติดต่อคนที่ถูกต้องได้เมื่อเกิดเหตุ
- **มีสองปุ่มให้เลือก** ปุ่ม "อัปเดตข้อมูลของฉัน" พาไปหน้าโปรไฟล์เพื่อแก้ไขได้ทันที และเมื่อกดบันทึกก็ถือว่าตรวจสอบแล้ว ส่วนปุ่ม "ไม่มีการเปลี่ยนแปลง ใช้ข้อมูลเดิม" จะเก็บข้อมูลเดิมไว้และป๊อปอัปจะไม่ขึ้นอีกจนกว่าจะครบ 3 เดือน
- ทุกคนที่มีโปรไฟล์ครบแล้วจะเห็นป๊อปอัปนี้หนึ่งครั้งหลังอัปเดตรอบนี้ เพราะยังไม่เคยตรวจสอบมาก่อน ส่วนคนที่ยังกรอกข้อมูลไม่ครบจะไปหน้ากรอกข้อมูลเหมือนเดิม
- มีข้อความภาษาอังกฤษ ไทย พม่า และจีน

## ฝั่งทีม (technical changelog)

### ป๊อปอัปตรวจสอบโปรไฟล์ทุก 3 เดือน (v2.23.0, commit `7abfea0`)

- **DB/migration:** เพิ่มคอลัมน์ `users.profile_reviewed_at` (timestamp, nullable) ใน migration `0047` เป็นการเพิ่มคอลัมน์อย่างเดียว ไม่มีการลบหรือแปลงข้อมูล ต้องรัน `npm run db:migrate:container` บน prod ก่อน merge ซึ่งยืนยันแล้วว่ารันแล้ว ค่า null หมายถึงยังไม่เคยตรวจสอบ จึงถึงกำหนดทันที
- **ทำไมไม่ใช้ `updatedAt`:** คอลัมน์นั้นถูกอัปเดตจากฟีเจอร์อื่นด้วย จะทำให้นาฬิกา 3 เดือนรีเซ็ตเงียบ ๆ จึงแยกคอลัมน์ใหม่
- **กฎเดียวใช้ร่วมกัน:** `src/lib/profile-review.ts` มี `isProfileReviewDue` และ `shouldShowProfileReview` (โปรไฟล์ต้องครบก่อนจึงจะถูกถาม) พร้อมเทสต์ใหม่ 3 ตัวในหน้าโปรไฟล์และหน้า dashboard
- **API:** `POST /api/profile/review` ตั้ง `profileReviewedAt` เท่านั้น ไม่แตะฟิลด์โปรไฟล์ และต้องเป็นโปรไฟล์ที่ครบแล้ว `PATCH /api/profile` และ onboarding (`POST`) ตั้งค่านี้ด้วย
- **PDPA:** ปุ่มเก็บข้อมูลเดิมเขียน audit log ใน transaction เดียวกัน ("Self: confirmed profile info unchanged") ไม่มีการอ่านข้อมูลสุขภาพเพิ่ม และ audit log เดิมของการแก้ไขข้อมูลสุขภาพยังทำงานตามเดิม
- **สิทธิ์เข้าถึง:** ไม่แก้ `src/proxy.ts` โปรไฟล์ที่ยังไม่ครบยังถูกส่งไป `/onboarding` เหมือนเดิม
- **UI:** เพิ่ม `ProfileReviewModal` และ `ProfileReviewGate` (dashboard ดึงโปรไฟล์ครั้งเดียวตอนเปิด) ปุ่มอัปเดตจาก dashboard ไปที่ `/dashboard/profile?review=update` เพื่อไม่ให้ป๊อปอัปซ้ำ ข้อความใหม่ 5 คีย์ใน `i18n.ts` (EN/TH/MM/CN)
- **Dev tooling:** เพิ่ม `npm run db:seed:test-student` สร้างนักศึกษาทดสอบ (ข้อมูลสมมติ, review date เป็น null) รันซ้ำแล้วรีเซ็ตแถวเดิม และปฏิเสธทุกฐานข้อมูลที่ไม่ใช่ localhost โดยไม่มีทางข้าม ต่างจาก `guard.ts` ที่ข้ามด้วย `CONFIRM=yes` ได้
- **Dev Bypass Login:** เปิดฟอร์มกลับมา (เดิมถูกปิดด้วย `false &&` ใน commit `9960aff`) ยังใช้ได้เฉพาะ `NODE_ENV=development` กับ `ENABLE_DEV_LOGIN=true` และปฏิเสธฐานข้อมูลระยะไกล เพื่อไม่ให้ dropdown ของ role เขียนทับอีเมลที่พิมพ์เอง จึงเปลี่ยนอีเมลเมื่อยังเป็นค่าสำเร็จรูปเท่านั้น ควรแจ้งคนที่ปิดฟอร์มไว้
- **เทสต์:** เพิ่มคอลัมน์ใหม่ใน DDL ของตาราง `users` ที่เขียนมือใน `battle-flow.test.ts` และ `stats-helper.test.ts` ไม่งั้นเทสต์ games ล้ม
- **ตรวจสอบแล้ว:** `npm run build` ผ่าน, `npm test` 368 ตัวผ่าน, `tsc` ผ่าน และ `npm run lint` ไม่มี error ใหม่ (มี error เดิมหนึ่งจุดใน `battle-flow.test.ts`) ทดสอบทั้งสองปุ่มบน Chrome กับ Postgres ชั่วคราวในเครื่อง แต่ยังไม่ได้ทดสอบบน prod และข้อความภาษาพม่ากับจีนยังไม่มีเจ้าของภาษาตรวจ

---

# ActiveCAMT v2.23.1 🎉

## ฝั่งทีม (technical changelog)

### เพิ่มคอลัมน์ของป๊อปอัปตรวจสอบโปรไฟล์ใน container migration (commit `f80709e`)

- **DB/migration:** เพิ่มขั้นที่ 99 ใน `src/db/migrate.ts` คือ `ALTER TABLE users ADD COLUMN IF NOT EXISTS profile_reviewed_at timestamptz` เป็นการเพิ่มคอลัมน์อย่างเดียว รันซ้ำได้ และไม่แตะข้อมูลเดิม
- **ที่มา:** v2.23.0 ใส่คอลัมน์นี้ไว้แค่ในไฟล์ `drizzle/0047` ซึ่ง `migrate.ts` บน Postgres ไม่ได้รัน เพราะเป็นรายการขั้นตอนที่เขียนเอง ดังนั้น `npm run db:migrate:container` จึงไม่ได้สร้างคอลัมน์ให้ และโค้ด v2.23.0 ที่ deploy ไปแล้วอ่านคอลัมน์นี้ ถ้า prod ยังไม่มีคอลัมน์ การดึงข้อมูลผู้ใช้จะพัง
- **สิ่งที่ต้องทำบน prod:** เพิ่มคอลัมน์ทันทีผ่าน console ของ `activecamt-db` ด้วย `psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c 'ALTER TABLE users ADD COLUMN IF NOT EXISTS profile_reviewed_at timestamptz;'` ไม่ต้องรอ deploy รอบนี้ และหลังจากนี้ `npm run db:migrate:container` จะเพิ่มให้เองถ้ายังไม่มี
- **ขั้นตอนการ ship:** ตามที่เจ้าของโปรเจกต์อนุมัติ commit นี้ push เข้า `main` โดยตรงโดยไม่เปิด PR
- **เวอร์ชัน:** `package.json` และ `package-lock.json` ปรับเป็น 2.23.1 ให้ตรงกับ tag
- **ตรวจสอบแล้ว:** รัน `migrate.ts` บน Postgres ชั่วคราวในเครื่องสองแบบ คือแบบที่มีคอลัมน์อยู่แล้ว และแบบที่ลบคอลัมน์ออกก่อน ทั้งสองแบบจบด้วย `✅ Migration complete!` และ `tsc` ผ่าน, `npm test` 368 ตัวผ่าน ยังไม่ได้ยืนยันบน prod

## ฝั่งทีม (technical changelog)

### หน้าร้านค้าและการแสดงผลบนมือถือ (v2.23.2, commit `5fa8b62`)

- **Mobile/UI:** `OrderHandover` ใน `ShopClient.tsx` พิมพ์ `order.pickupInfo` ตรง ๆ แต่ฝั่ง checkout ใช้ `parseRichText` อยู่แล้ว จึงเพิ่มคอมโพเนนต์ `PickupInfo` ที่ผ่าน `parseRichText` และใช้ทั้งสองจุด (กล่องเตรียมสินค้ากับกล่องรับของบางส่วน)
- **iOS zoom:** `globals.css` ตั้ง `font-size: 16px !important` ให้ `textarea`, `select` และ `input` ทุกชนิดที่เป็นช่องพิมพ์ ภายใต้ `@media (hover: none) and (pointer: coarse)` เพราะ Safari ซูมหน้าเมื่อโฟกัสช่องที่เล็กกว่า 16px เลือกเงื่อนไขตามชนิดอุปกรณ์ ไม่ใช่ความกว้างจอ เพื่อให้ครอบคลุมมือถือที่รายงานความกว้างมากด้วย ยกเว้น `date`, `datetime-local` และ `time` เพราะมีกฎขนาดเล็กของมันเองอยู่แล้ว กฎนี้มีผลกับฝั่งแอดมินบนอุปกรณ์สัมผัสด้วย และเพิ่ม `text-size-adjust: 100%` กัน iOS ขยายตัวอักษรเอง
- **Layout:** แถวแท็บใช้ `flexWrap`, กริดสินค้าใช้ `minmax(min(220px,100%),1fr)` และป๊อปอัปชำระเงินใช้ `94dvh` แทน `94vh` เพราะ `vh` บน iOS รวมแถบเครื่องมือของเบราว์เซอร์
- **ยังไม่พบสาเหตุ:** อาการที่ Android จอใหญ่แสดงเป็นเลย์เอาต์แท็บเล็ต ซึ่งหน้า `/dashboard/id` ไม่มีเลย์เอาต์แท็บเล็ตเลย (คอลัมน์เดียวกว้างสูงสุด 480px) สมมติฐานคือมือถือบางรุ่นรายงานความกว้างเกิน 640px จึงติดเบรกพอยต์ `sm:` กับ `md:` ของหน้าอื่นอย่าง onboarding และ history ยังไม่ได้แก้ ต้องการภาพหน้าจอและรุ่นเครื่องจากผู้ใช้
- **Workflow:** ตามที่เจ้าของโปรเจกต์ตัดสินใจเพื่อประหยัดเวลา สกิล `/ship` ปรับให้ commit และ push เข้า `main` โดยตรง ไม่ผ่าน feature branch หรือ PR อีกต่อไป และการ push เข้า `main` จะ redeploy prod ผ่าน webhook ทันที จึงต้อง migrate prod ก่อนเสมอถ้ามีการเปลี่ยน schema
- **เวอร์ชัน:** `package.json` และ `package-lock.json` ปรับเป็น 2.23.2 ให้ตรงกับ tag
- **ตรวจสอบแล้ว:** `npm run build` ผ่าน และ `npm run lint` ไม่มี error ใหม่ (มี error เดิมหนึ่งจุดใน `battle-flow.test.ts`) ทดสอบข้อความจุดรับสินค้าบน Chrome กับ Postgres ชั่วคราวในเครื่อง และไม่พบ element ล้นจอในหน้าร้านค้าที่ความกว้าง 550px ส่วนการซูมของ iPhone ยังไม่ได้ทดสอบบนเครื่องจริง เพราะ Chrome บนเดสก์ท็อปไม่เข้าเงื่อนไขอุปกรณ์สัมผัส

# ActiveCAMT v2.23.3 🎉

## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **สถานะคำสั่งซื้อในร้านค้าชัดเจนขึ้น** เมื่อชำระเงินแล้ว ป้ายจะไม่ขึ้นว่า "พร้อมรับ" อีกต่อไป สินค้ารับเองจะขึ้นว่า "ชำระแล้ว · กำลังเตรียมสินค้า" จนกว่าผู้ขายจะแจ้งว่าพร้อมรับ ส่วนสินค้าจัดส่งจะแยกระหว่าง "กำลังเตรียมจัดส่ง" "จัดส่งแล้ว" และ "ได้รับสินค้าแล้ว"
- **คำแนะนำให้แสดงคิวอาร์โค้ดประจำตัว** จะขึ้นเฉพาะเมื่อสินค้าพร้อมรับแล้ว เพื่อไม่ให้เข้าใจผิดว่าต้องไปรับตอนนี้เลย
- **ใช้ชื่อเดียวกับในแอป** เรียกว่า "คิวอาร์โค้ดประจำตัว" แทนคำว่า Digital ID ในหน้าร้านค้า

- ร้านค้า: เพิ่ม `orderBadge()` ใน `src/app/dashboard/shop/ShopClient.tsx` สร้างป้ายสถานะจากสถานะการชำระเงินและขั้นตอนการจัดส่งรวมกัน
- ร้านค้า: ย้ายคำแนะนำ "แสดงคิวอาร์โค้ดประจำตัว" และปุ่มเปิดคิวอาร์โค้ด ให้แสดงเฉพาะเมื่อ `fulfillmentStatus === "ready"`
- ไม่มีการเปลี่ยนแปลงฐานข้อมูลหรือ migration, ไม่กระทบสิทธิ์เข้าถึงและข้อมูลทางการแพทย์

# ActiveCAMT v2.24.0 🎉

## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **มีโหมดมืดให้ใช้แล้ว** กดปุ่มพระจันทร์หรือดวงอาทิตย์บนแถบเมนูด้านบนเพื่อสลับระหว่างโหมดสว่างกับโหมดมืดได้ทุกหน้า ช่วยให้อ่านสบายตาขึ้นเวลาใช้ตอนกลางคืนหรือในที่มืด
- **ระบบจำค่าที่เลือกไว้** เปิดเว็บครั้งต่อไปจะเป็นโหมดเดิมที่เลือก ส่วนคนที่เข้าครั้งแรกจะใช้ตามการตั้งค่าของเครื่อง (สว่างหรือมืด) โดยหน้าจะไม่กะพริบเป็นสีผิดตอนโหลด
- **คิวอาร์โค้ดยังเป็นพื้นขาวตัวดำในทุกโหมด** เพื่อให้สแกนติดง่ายเหมือนเดิม

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **โหมดมืดใช้ได้ในหน้าแอดมินทั้งหมด** ปุ่มสลับอยู่ในแถบเมนูด้านข้างและแถบด้านบนบนมือถือ ได้ตรวจหน้าภาพรวม กิจกรรม (รวมฟอร์มสร้างกิจกรรม) สแกนเนอร์ ร้านค้า รายชื่อผู้ใช้ ประกาศ และชมรมแล้ว
- **รายงานรางวัลที่สั่งพิมพ์จะเป็นโหมดสว่างเสมอ** เพื่อให้พิมพ์ออกมาเป็นกระดาษขาวปกติ

## ฝั่งทีม (technical changelog)

### โหมดมืดและชุดสีกลาง (v2.24.0, commit `8301e11`)

- **Mobile/UI:** เพิ่ม `ThemeToggle` (`src/components/ui/ThemeToggle.tsx`) และ `src/lib/theme.ts` ธีมเก็บเป็น attribute `data-theme` บน `<html>` และเก็บค่าที่เลือกใน `localStorage` คีย์ `theme` สคริปต์ inline ใน `<head>` ของ `layout.tsx` ตั้งค่าก่อน paint (ใช้ค่าที่บันทึกไว้ ถ้าไม่มีใช้ `prefers-color-scheme`) จึงไม่มีการกะพริบ และก่อนพิมพ์จะสลับเป็น light ชั่วคราวผ่าน `beforeprint`/`afterprint` ปุ่มอยู่ใน `StudentNav`, `AdminNav`, `AdminLayoutWrapper` (มือถือ) และการ์ดใน `LandingUI` ไม่ได้เพิ่มไลบรารีใหม่
- **ชุดสีกลาง:** `globals.css` มี token ของธีมเดิมพร้อมค่าโหมดมืด และชุดสีใหม่ตามบทบาท (`--red-500`, `--teal-600`, `--neutral-300` ฯลฯ) พร้อมตัวแปร `-rgb` สำหรับสีโปร่งใส สีเข้มที่ใช้เป็นตัวอักษรจะสว่างขึ้นในโหมดมืด ส่วนสีอ่อนที่ใช้เป็นพื้นหลังจะกลายเป็นพื้นโปร่งมืด สีที่ไม่สลับธีมมี `--white`, `--text-on-color`, `--qr-surface`, `--media-bg` และ `*-fill`
- **การแปลงโค้ด:** แทนที่ hex และ rgba ที่เขียนตรง ๆ ในไฟล์ 62 ไฟล์ด้วย token ผ่านสคริปต์ แล้วตรวจแก้เองในจุดที่พื้นหลังขาวจะชนกับตัวอักษรที่สลับสี (ชิปวันที่บน dashboard, ตัวสลับภาษา, จุดขั้นตอนใน onboarding, จุดสไลด์โปสเตอร์) เพิ่ม `alpha()` ใน `src/lib/color.ts` (มีเทสต์ 3 ตัว) แทนการต่อเลขฐานสิบหกท้ายสี เพราะวิธีเดิมใช้ไม่ได้เมื่อสีเป็น `var()` และใช้ `color-mix`
- **สิ่งที่ตั้งใจไม่แปลง:** สีธงใน `LanguageSwitcher`, โลโก้ Google, `bgColor`/`fgColor` ของ QR, ค่าเริ่มต้นของ `<input type="color">`, สีเลขหน้าใน `@page` ของรายงานรางวัล (CSS ในกล่องขอบหน้าไม่อ่านตัวแปร) และสีบ้านใน `faculties.ts` เพราะเป็นข้อมูลที่ตรงกับ seed
- **QR:** `color-scheme: only light` ยังคงอยู่ในธีมสว่างเพื่อกัน auto-dark ของเบราว์เซอร์ และพื้นหลัง QR ทุกจุดใช้ `--qr-surface` (ขาว) ส่วน `<meta color-scheme>` เปลี่ยนเป็น `light dark`
- **i18n:** เพิ่มคีย์ `themeSwitchToDark` และ `themeSwitchToLight` ใน EN/TH/MM/CN (ใช้เป็น aria-label)
- **ไม่มี migration, ไม่กระทบสิทธิ์เข้าถึงและข้อมูลทางการแพทย์**
- **ตรวจสอบแล้ว:** `npm run build` ผ่าน, `npm test` 371 ตัวผ่าน และ `npm run lint` ไม่มี error ใหม่ (มี error เดิมหนึ่งจุดใน `battle-flow.test.ts`) ดูโหมดมืดบน Chrome แล้ว 7 หน้า ที่ยังไม่ได้ตรวจคือหน้าที่ต้องมีข้อมูลจริง เช่น รายการกิจกรรมที่มีโปสเตอร์ แท็บคำสั่งซื้อของร้านค้า และรายงานรางวัล
- **เวอร์ชัน:** `package.json` และ `package-lock.json` ปรับเป็น 2.24.0 ให้ตรงกับ tag
