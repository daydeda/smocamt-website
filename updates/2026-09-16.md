# ActiveCAMT v2.6.0 🎉

# อัปเดต ActiveCAMT ประจำวันที่ 16 ก.ย. 69

สรุปสำหรับวันที่ 16 ก.ย. 69 เอาไว้ลง Discord และให้ทีมที่เกี่ยวข้องอ่านกัน

---

## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **นักศึกษาทุกคน ไม่ใช่แค่ประธานชมรม/สาขา สมัครเป็นผู้ขายในร้านค้าได้เองแล้ว** เมื่อได้รับอนุมัติจะมี QR ชำระเงิน ข้อความแจ้งการชำระเงิน ค่าส่งแบบเหมาจ่าย และช่องทางรับของเป็นของตัวเอง ไม่ต้องใช้ของร้านกลางอีกต่อไป
- **สินค้าที่ผู้ขายรายใหม่ลงขาย จะยังไม่ขึ้นหน้าร้านจนกว่าทีมงานจะตรวจและอนุมัติก่อน** เพื่อความปลอดภัยของผู้ซื้อ และถ้าผู้ขายแก้ไขสินค้าที่เคยอนุมัติแล้ว สินค้าจะถูกซ่อนกลับไปรออนุมัติใหม่ทุกครั้งเช่นกัน
- **สั่งซื้อจากผู้ขายแต่ละรายจะแยกเป็นคนละออเดอร์กัน** ระบบไม่ให้ปนสินค้าจากหลายผู้ขายไว้ในออเดอร์เดียว
- **กิจกรรมที่ต้องไปทำนอกสถานที่ (เช่น เก็บก้าว) จะมีการเช็คอิน 2 ครั้งได้แล้ว** สแกน QR ตอนไปเริ่มกิจกรรม แล้วกลับมาสแกนอีกครั้งพร้อมโชว์หลักฐาน (เช่น ภาพหน้าจอ Strava) ให้เจ้าหน้าที่ตรวจก่อนยืนยัน ถึงจะได้คะแนนของวันนั้น ทั้งนี้ใช้เฉพาะกิจกรรมที่แอดมินเปิดใช้ฟีเจอร์นี้เท่านั้น กิจกรรมทั่วไปเช็คอินครั้งเดียวเหมือนเดิม

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **มีคิวตรวจสอบผู้สมัครขายของใหม่** ให้ admin, super_admin หรือ SMO ฝ่ายการเงิน (finance) กดอนุมัติ ปฏิเสธ ระงับ หรือคืนสิทธิ์ผู้ขายได้ พร้อมบันทึก audit log ทุกครั้ง
- **role ใหม่ `shop_seller` เข้าหน้า `/admin/shop` ได้แบบจำกัดขอบเขต** เหมือน role `smo` ที่เข้าได้แค่ `/admin/scanner`
- **ระงับสิทธิ์ผู้ขายรายใดมีผลทันที** สินค้าของผู้ขายนั้นหายจากหน้าร้าน เรียก API ไม่ได้ และคำสั่งซื้อที่ค้างอยู่จะตรวจสอบต่อไม่ได้จนกว่าจะคืนสิทธิ์
- **ประธานชมรม/สาขาไม่ต้องสมัครและรออนุมัติเป็นผู้ขายซ้ำอีกแล้ว** เพราะสิทธิ์ประธานผ่านการตรวจสอบจากการแต่งตั้งชมรม/สาขาอยู่แล้ว ตอนนี้เปิดหน้า "จัดการร้านค้า" ครั้งแรกจะได้สิทธิ์ผู้ขายที่อนุมัติแล้วทันที สร้างสินค้าและตั้งค่า QR รับเงินได้เลยโดยไม่ต้องรอแอดมิน ส่วนถ้าแอดมินเคยระงับหรือปฏิเสธประธานคนไหนไว้ สิทธิ์นั้นยังคงถูกระงับเหมือนเดิม
- **ตัวเลือก "Require check-out" ใหม่ในหน้าแก้ไขกิจกรรม (`/admin/events`)** เปิดให้กิจกรรมนั้นต้องเช็คอิน 2 ครั้งแทนครั้งเดียว สแกนแรกแค่บันทึกว่ามาถึงแล้ว ยังไม่ได้คะแนน จนกว่าจะมีการสแกนซ้ำตอนกลับมา ซึ่งหน้าสแกน (`/admin/scanner`) จะขึ้นให้แนบรูปหลักฐานก่อนกดยืนยันเช็คเอาท์ รูปที่แนบจะถูกเก็บไว้เป็นหลักฐานถาวร ดูย้อนหลังได้ ถ้าพบว่าเป็นหลักฐานปลอมภายหลัง ใช้เครื่องมือหักคะแนนที่มีอยู่เดิมได้เลย ไม่ต้องทำอะไรเพิ่ม
- **มีอีกฟีเจอร์หนึ่งที่เตรียมไว้แต่ยังไม่ได้เปิดใช้กับกิจกรรมไหน** คือให้นักศึกษาส่งรูปหลักฐาน + รหัสประจำวันด้วยตนเองผ่านแอป โดยไม่ต้องมีเจ้าหน้าที่คอยสแกนเลย (auto-award ทันทีที่ส่ง) เผื่อไว้สำหรับกิจกรรมที่ไม่มีเจ้าหน้าที่ประจำจุดเลยในอนาคต

## ฝั่งทีม (technical changelog)

### ระบบร้านค้าหลายผู้ขายพร้อมการอนุมัติที่น่าเชื่อถือ (PR #227, merge commit `7d5d01d`)

- **DB/migration:** เพิ่มตาราง `shop_sellers` ใหม่ พร้อมคอลัมน์ `seller_id` แบบ nullable ใน `shop_products`/`shop_orders`, `approval_status`, `approval_reason` และ `checkout_group_id` FK ของ seller→user และ seller→product ใช้ `ON DELETE RESTRICT` กันไม่ให้ลบ user/seller แล้วสินค้าที่อนุมัติแล้วเงียบ ๆ กลายเป็นสินค้าส่วนกลาง ส่วน order→seller ใช้ `ON DELETE SET NULL` เก็บประวัติออเดอร์เดิมไว้ migration เป็น additive/idempotent ทั้งหมด (`drizzle/0038_nice_whizzer.sql`) สินค้า/ออเดอร์เดิมยังใช้ค่า default เดิมได้ปกติ ยังไม่ได้รันบน prod ต้องรัน `npm run db:migrate:container` จาก Portainer console ก่อน deploy image ใหม่ (ดู `/safe-deploy`)
- **สิทธิ์เข้าถึง (4 layer):** เพิ่ม role `shop_seller` ใน `admin-access.ts` (`ADMIN_ENTRY_ROLES`, `SCANNER_ONLY_ROLES`) ให้ `proxy.ts`, admin layout, `admin-nav-config.ts` และทุก route ฝั่ง server ภายใต้ `api/admin/shop` กับ `api/shop` ยึด `resolveShopAccess` (`shop-scope.ts`) เป็นแหล่งความจริงเดียว โดย query สถานะผู้ขายจากฐานข้อมูลทุกครั้ง ไม่พึ่ง session/JWT เดิม กัน session ค้างของผู้ขายที่โดนระงับหรือถูกปฏิเสธไม่ให้เข้าถึงต่อได้ เพิ่ม `isShopFinancePosition` ให้ `smo` ที่มีตำแหน่ง finance เป็น reviewer ได้ด้วย
- **Route ใหม่:** `POST /api/shop/seller` (สมัครเป็นผู้ขาย เปิดให้ทุก Google account ไม่จำกัดโดเมนตามที่ตั้งใจไว้) และ `GET`/`PATCH /api/admin/shop/sellers`, `/api/admin/shop/sellers/[id]` (คิวตรวจสอบผู้ขาย อนุมัติ/ปฏิเสธ/ระงับ/คืนสิทธิ์ ทำแบบ transaction พร้อม audit log)
- **Product approval:** สินค้าที่ผู้ขาย/ประธานสร้างเริ่มที่สถานะ `pending` และต้องให้ reviewer ที่ไม่ scoped (admin/super_admin หรือ SMO การเงิน) กดอนุมัติก่อนถึงจะโชว์หน้าร้าน ถ้าผู้ขาย/ประธานแก้ไขสินค้าที่อนุมัติแล้ว ระบบรีเซ็ตกลับเป็น `pending` อัตโนมัติทุกครั้ง กันไม่ให้สลับเนื้อหาหลังผ่านการตรวจแล้ว
- **Order/slip scoping:** `/api/shop/orders` ปฏิเสธ payload ที่ปนสินค้าจากหลายผู้ขาย และ fallback ค่าจัดส่งจากผู้ขายเมื่อไม่ได้ระบุ `/api/admin/shop/orders/[id]` กับ `/api/shop/orders/[id]/slip` ล็อกแถว `shop_sellers` แบบ `FOR UPDATE`/`FOR SHARE` ระหว่างธุรกรรม กันไม่ให้อนุมัติ/ปฏิเสธออเดอร์หลุดผ่านไปได้ในจังหวะเดียวกับที่ผู้ขายเพิ่งถูกระงับ
- **PDPA/audit:** ข้อมูลที่แตะในรอบนี้เป็นข้อมูลร้านค้า/การเงิน (สลิปโอนเงิน ที่อยู่จัดส่ง) ไม่ใช่ข้อมูลการแพทย์ การเข้าถึงสลิปโดยคนที่ไม่ใช่เจ้าของยังเขียน audit log เหมือนเดิม
- ตรวจสอบแล้วด้วย `npm test` (202 ผ่านทั้งหมด), `npx tsc --noEmit`, targeted ESLint (ไม่มี error ใหม่), และ `npx next build --webpack` ผ่านครบ ส่วน `npm run lint` เต็มรูปแบบยังเจอ error เดิมที่ไม่เกี่ยวข้องใน `src/app/api/battle/rooms/battle-flow.test.ts` เท่านั้น พร้อม runtime verification บน local Docker Postgres ครบทุกขั้นตอน ตั้งแต่สมัคร อนุมัติ ตั้งค่าผู้ขาย สร้างสินค้า อนุมัติสินค้า สั่งซื้อ เข้าถึงออเดอร์/สลิปแบบจำกัดสิทธิ์ ระงับ ไปจนถึงคืนสิทธิ์

### ประธานชมรม/สาขาไม่ต้องรออนุมัติผู้ขายอีกต่อไป (PR #228, merge commit `8daf2f6`)

- **แก้ regression จาก PR #227:** `resolveShopAccess` (`src/lib/shop-scope.ts`) เดิมบังคับให้ทุกบัญชี scoped ต้องมี `shop_sellers` ที่สถานะ `approved` ก่อนจึงจะสร้างสินค้าหรือแก้ไขค่า QR/การชำระเงินได้ ซึ่งรวมถึงประธานชมรม/สาขาที่ผ่านการตรวจสอบจาก `club_members`/สาขาอยู่แล้วด้วย ทำให้ประธานติดอยู่ที่ข้อความ "ต้องสมัครและรออนุมัติก่อน" ทั้งที่ควรใช้งานได้ทันที
- **พฤติกรรมใหม่:** เมื่อประธานเข้า `/admin/shop` ครั้งแรกโดยยังไม่มีแถวผู้ขาย ระบบจะสร้างแถว `shop_sellers` สถานะ `approved` ให้อัตโนมัติ ส่วนแถวเดิมที่ค้างสถานะ `pending` (จากก่อนแก้ไข) จะถูกเลื่อนเป็น `approved` ให้อัตโนมัติเช่นกัน แต่ถ้าแอดมินเคยตั้งสถานะเป็น `suspended`/`rejected` ไว้อย่างจงใจ ระบบจะไม่แตะต้องค่านั้น สิทธิ์ยังคงถูกระงับตามเดิม ผู้ขายที่ไม่ใช่ประธาน (สมัครแบบ Google account ทั่วไป) ยังต้องผ่านคิวอนุมัติของแอดมินเหมือนเดิมทุกประการ
- ตรวจสอบแล้วด้วย `npm test` (202 ผ่านทั้งหมด), `npx tsc --noEmit`, targeted ESLint, และ `npx next build --webpack` ผ่านครบ พร้อมทดสอบจริงบน local Docker Postgres ผ่าน dev-login bypass ครบทั้งกรณีประธานใหม่ ประธานที่มีแถว pending ค้างอยู่ การสร้างสินค้า การบันทึกค่า QR/การชำระเงิน และยืนยันว่าสถานะ suspended ยังกันสิทธิ์ได้เหมือนเดิม

### เช็คอิน/เช็คเอาท์แบบมีเจ้าหน้าที่ตรวจสอบ สำหรับกิจกรรมนอกสถานที่ (PR #229, merge commit `4524614`)

- **DB/migration:** เพิ่ม `events.check_in_mode` (default `'qr'`), `events.require_check_out` (default `false`), `event_sessions.evidence_nonce`/`evidence_prompt`, และ `attendance.check_out_time`/`evidence_file_key`/`evidence_nonce_submitted` ทุกคอลัมน์เป็น additive/idempotent ไม่กระทบกิจกรรมเดิมเลยเพราะ default เป็นพฤติกรรมเดิมทั้งหมด (`drizzle/0039_brief_paibok.sql`, `drizzle/0040_skinny_dark_phoenix.sql`) สำคัญ: สคริปต์ที่รันจริงบน prod คือ `src/db/migrate.ts` (steps 91-92 ที่เพิ่มในรอบนี้) ไม่ใช่ไฟล์ SQL ที่ Drizzle generate ให้ เพราะ `db:migrate:container` ไม่ได้อ่านโฟลเดอร์ `drizzle/` โดยตรงสำหรับ Postgres จริง รันทดสอบซ้ำบน local Docker Postgres แล้วว่า idempotent และคอลัมน์ขึ้นถูกต้องตาม type/default ยังไม่ได้รันบน prod ต้องรัน `npm run db:migrate:container` จาก Portainer console ก่อน deploy image ใหม่
- **Two-step check-in/check-out:** แก้ `ScannerService.processScan` แบบ additive เท่านั้น คือครอบเงื่อนไข `if (event.requireCheckOut)` ที่จุดให้คะแนน 3 จุด (ทำให้สแกนแรกไม่ให้คะแนนทันที) เพิ่มเงื่อนไขใหม่ที่จุดตรวจ "เช็คอินแล้ว" ให้แยกว่าเป็นการสแกนกลับมาเช็คเอาท์ (`pending_checkout`) หรือซ้ำซ้อนจริง ๆ และเพิ่ม method `confirmCheckout` ใหม่ที่บังคับต้องมีรูปหลักฐานก่อนถึงจะให้คะแนน กิจกรรมที่ไม่ได้เปิด `requireCheckOut` (ค่า default) ไม่ถูกแตะต้องเลยแม้แต่บรรทัดเดียว
- **Route ใหม่:** action `confirm_checkout` ใน `POST /api/admin/scan` (ต้องแนบ `evidenceFileKey`) และหน้าสแกน `/admin/scanner` มี UI ใหม่สำหรับแนบรูปหลักฐาน + ปุ่ม "Confirm Check-out" เมื่อสถานะเป็น `pending_checkout`
- **Self-service evidence check-in (dormant):** เพิ่ม `events.checkInMode: 'evidence'` เป็นอีกทางเลือกสำหรับกิจกรรมที่ไม่มีเจ้าหน้าที่ประจำจุดเลย มี pure logic + unit test แยกที่ `src/lib/evidence-checkin.ts` (ตรวจ nonce/ช่วงเวลาเปิดรับ) และ service `evidence-checkin.service.ts` แต่ยังไม่ได้ผูกกับกิจกรรมไหนจริง เก็บไว้ใช้ในอนาคต
- **PDPA:** รูปหลักฐานเก็บใน private bucket เดียวกับไฟล์แนบของฟอร์ม (`form-uploads`) ไม่ใช่ public URL ดูได้เฉพาะเจ้าของหรือ staff ผ่าน `/api/attendance/evidence/[attendanceId]` ที่มี auth guard การดูของ staff ที่ไม่ใช่เจ้าของถูกบันทึก audit log ทุกครั้ง
- ตรวจสอบแล้วด้วย `npm test` (216 ผ่านทั้งหมด), `npx tsc --noEmit`, `npm run lint`, และ `npm run build` ผ่านครบทุกจุด ส่วนโค้ดที่แตะ `ScannerService` โดยตรงยังไม่มี automated test คลุม (เป็น DB-orchestration logic) แนะนำให้ `/verify` กับกิจกรรมจริงก่อนใช้งานจริง
