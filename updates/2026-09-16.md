# ActiveCAMT v2.5.0 🎉

# อัปเดต ActiveCAMT ประจำวันที่ 16 ก.ย. 69

สรุปสำหรับวันที่ 16 ก.ย. 69 เอาไว้ลง Discord และให้ทีมที่เกี่ยวข้องอ่านกัน

---

## ฝั่งนักศึกษา (สิ่งที่ user จะเห็น)

- **นักศึกษาทุกคน ไม่ใช่แค่ประธานชมรม/สาขา สมัครเป็นผู้ขายในร้านค้าได้เองแล้ว** เมื่อได้รับอนุมัติจะมี QR ชำระเงิน ข้อความแจ้งการชำระเงิน ค่าส่งแบบเหมาจ่าย และช่องทางรับของเป็นของตัวเอง ไม่ต้องใช้ของร้านกลางอีกต่อไป
- **สินค้าที่ผู้ขายรายใหม่ลงขาย จะยังไม่ขึ้นหน้าร้านจนกว่าทีมงานจะตรวจและอนุมัติก่อน** เพื่อความปลอดภัยของผู้ซื้อ และถ้าผู้ขายแก้ไขสินค้าที่เคยอนุมัติแล้ว สินค้าจะถูกซ่อนกลับไปรออนุมัติใหม่ทุกครั้งเช่นกัน
- **สั่งซื้อจากผู้ขายแต่ละรายจะแยกเป็นคนละออเดอร์กัน** ระบบไม่ให้ปนสินค้าจากหลายผู้ขายไว้ในออเดอร์เดียว

---

## ฝั่งแอดมิน/ทีมงาน (สิ่งที่ staff จะเห็น)

- **มีคิวตรวจสอบผู้สมัครขายของใหม่** ให้ admin, super_admin หรือ SMO ฝ่ายการเงิน (finance) กดอนุมัติ ปฏิเสธ ระงับ หรือคืนสิทธิ์ผู้ขายได้ พร้อมบันทึก audit log ทุกครั้ง
- **role ใหม่ `shop_seller` เข้าหน้า `/admin/shop` ได้แบบจำกัดขอบเขต** เหมือน role `smo` ที่เข้าได้แค่ `/admin/scanner`
- **ระงับสิทธิ์ผู้ขายรายใดมีผลทันที** สินค้าของผู้ขายนั้นหายจากหน้าร้าน เรียก API ไม่ได้ และคำสั่งซื้อที่ค้างอยู่จะตรวจสอบต่อไม่ได้จนกว่าจะคืนสิทธิ์

## ฝั่งทีม (technical changelog)

### ระบบร้านค้าหลายผู้ขายพร้อมการอนุมัติที่น่าเชื่อถือ (PR #227, merge commit `7d5d01d`)

- **DB/migration:** เพิ่มตาราง `shop_sellers` ใหม่ พร้อมคอลัมน์ `seller_id` แบบ nullable ใน `shop_products`/`shop_orders`, `approval_status`, `approval_reason` และ `checkout_group_id` FK ของ seller→user และ seller→product ใช้ `ON DELETE RESTRICT` กันไม่ให้ลบ user/seller แล้วสินค้าที่อนุมัติแล้วเงียบ ๆ กลายเป็นสินค้าส่วนกลาง ส่วน order→seller ใช้ `ON DELETE SET NULL` เก็บประวัติออเดอร์เดิมไว้ migration เป็น additive/idempotent ทั้งหมด (`drizzle/0038_nice_whizzer.sql`) สินค้า/ออเดอร์เดิมยังใช้ค่า default เดิมได้ปกติ ยังไม่ได้รันบน prod ต้องรัน `npm run db:migrate:container` จาก Portainer console ก่อน deploy image ใหม่ (ดู `/safe-deploy`)
- **สิทธิ์เข้าถึง (4 layer):** เพิ่ม role `shop_seller` ใน `admin-access.ts` (`ADMIN_ENTRY_ROLES`, `SCANNER_ONLY_ROLES`) ให้ `proxy.ts`, admin layout, `admin-nav-config.ts` และทุก route ฝั่ง server ภายใต้ `api/admin/shop` กับ `api/shop` ยึด `resolveShopAccess` (`shop-scope.ts`) เป็นแหล่งความจริงเดียว โดย query สถานะผู้ขายจากฐานข้อมูลทุกครั้ง ไม่พึ่ง session/JWT เดิม กัน session ค้างของผู้ขายที่โดนระงับหรือถูกปฏิเสธไม่ให้เข้าถึงต่อได้ เพิ่ม `isShopFinancePosition` ให้ `smo` ที่มีตำแหน่ง finance เป็น reviewer ได้ด้วย
- **Route ใหม่:** `POST /api/shop/seller` (สมัครเป็นผู้ขาย เปิดให้ทุก Google account ไม่จำกัดโดเมนตามที่ตั้งใจไว้) และ `GET`/`PATCH /api/admin/shop/sellers`, `/api/admin/shop/sellers/[id]` (คิวตรวจสอบผู้ขาย อนุมัติ/ปฏิเสธ/ระงับ/คืนสิทธิ์ ทำแบบ transaction พร้อม audit log)
- **Product approval:** สินค้าที่ผู้ขาย/ประธานสร้างเริ่มที่สถานะ `pending` และต้องให้ reviewer ที่ไม่ scoped (admin/super_admin หรือ SMO การเงิน) กดอนุมัติก่อนถึงจะโชว์หน้าร้าน ถ้าผู้ขาย/ประธานแก้ไขสินค้าที่อนุมัติแล้ว ระบบรีเซ็ตกลับเป็น `pending` อัตโนมัติทุกครั้ง กันไม่ให้สลับเนื้อหาหลังผ่านการตรวจแล้ว
- **Order/slip scoping:** `/api/shop/orders` ปฏิเสธ payload ที่ปนสินค้าจากหลายผู้ขาย และ fallback ค่าจัดส่งจากผู้ขายเมื่อไม่ได้ระบุ `/api/admin/shop/orders/[id]` กับ `/api/shop/orders/[id]/slip` ล็อกแถว `shop_sellers` แบบ `FOR UPDATE`/`FOR SHARE` ระหว่างธุรกรรม กันไม่ให้อนุมัติ/ปฏิเสธออเดอร์หลุดผ่านไปได้ในจังหวะเดียวกับที่ผู้ขายเพิ่งถูกระงับ
- **PDPA/audit:** ข้อมูลที่แตะในรอบนี้เป็นข้อมูลร้านค้า/การเงิน (สลิปโอนเงิน ที่อยู่จัดส่ง) ไม่ใช่ข้อมูลการแพทย์ การเข้าถึงสลิปโดยคนที่ไม่ใช่เจ้าของยังเขียน audit log เหมือนเดิม
- ตรวจสอบแล้วด้วย `npm test` (202 ผ่านทั้งหมด), `npx tsc --noEmit`, targeted ESLint (ไม่มี error ใหม่), และ `npx next build --webpack` ผ่านครบ ส่วน `npm run lint` เต็มรูปแบบยังเจอ error เดิมที่ไม่เกี่ยวข้องใน `src/app/api/battle/rooms/battle-flow.test.ts` เท่านั้น พร้อม runtime verification บน local Docker Postgres ครบทุกขั้นตอน ตั้งแต่สมัคร อนุมัติ ตั้งค่าผู้ขาย สร้างสินค้า อนุมัติสินค้า สั่งซื้อ เข้าถึงออเดอร์/สลิปแบบจำกัดสิทธิ์ ระงับ ไปจนถึงคืนสิทธิ์
